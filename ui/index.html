Privacy Policy & Telemetry Governance

Effective Date: October 2026 | Compliance Scope: DPDP Act 2023 (India) & Local AppSec Data Isolation Standard

1. Zero External Telemetry & Local-First Storage

CyberForge Correlate processes all Abstract Syntax Tree (AST) route signatures, Static Application Security Testing (SAST) slices, Dynamic Application Security Testing (DAST) HTTP exchanges, and Software Composition Analysis (SCA) dependency graphs strictly within your local SQLite workspace database. No source code snippets, HTTP payloads, or vulnerability metadata are transmitted to third-party cloud endpoints.

2. Server-Side Credential Isolation

All runtime secrets, environment tokens, and database paths are isolated on the backend API server. The browser client never receives, stores, or transmits raw API keys or target credentials.

3. Ephemeral Canary Payloads

Active DAST verification uses deterministic, non-destructive `cyberforge` canary tokens and bounded sleep differentials against authorized loopback or container endpoints. Payloads do not mutate persistent customer records.

Terms of Use & Authorized Target Scope

Security Operations Governance: Mandatory Target Safety Lock Policy

1. Authorized Target Scope Only

CyberForge Correlate enforces a strict server-side Target Safety Lock (`validate_target_url_scope`). Active 2-phase DAST probing is restricted to loopback interfaces (`127.0.0.1`, `localhost`, `::1`), RFC1918 private container networks, or explicitly configured host allowlists (`CYBERFORGE_ALLOWED_HOSTS`).

2. Prohibition of Unauthorized Probing

Attempting to point active DAST scans at unauthorized external domains will be rejected immediately with HTTP `403 Target Safety Lock Violation`. Operators are solely responsible for ensuring written authorization before adding custom container hostnames to the server allowlist.

3. Deterministic Evidence Verification

A status of `Confirmed` indicates deterministic agreement between static code paths and runtime HTTP verification. Operators should review `NeedsVerification` findings before production release sign-off.

1. AST Route Discovery & Decoy Suppression

Conventional scanners flood teams with false positives on parameterized SQL queries, HTML-escaped templates, and allowlisted redirects. CyberForge parses your source AST first, maps every route signature, and suppresses provably safe decoys before DAST runs.

AST Route Mapper -> SAST Sink Detection -> Safe Decoy Gate (Suppresses False Positives)

2. 2-Phase Baseline vs Attack DAST

Every candidate route undergoes a benign baseline request (Phase 1) followed by targeted CWE-specific canary probes (Phase 2). If the vulnerable sink lives in a helper module (`services/order_service.py`), the correlator bridges the call graph back to the HTTP route.

Confirmed = SAST Sink + DAST Phase-2 Differential Proof on Canonical Route + CWE

3. Deterministic Fingerprints & Idempotency

Every correlated issue receives a deterministic `correlate:v1:` SHA-256 fingerprint. Running a scan twice (`Verify Idempotency (2x)`) performs an atomic SQLite upsert without duplicating issues.

Target Safety Lock: Active DAST probes are strictly locked to loopback/container hosts.
